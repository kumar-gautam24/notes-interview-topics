## Part A — What are subscriptions? (Concept)

### One-time payment vs subscription

What you already have in this project:

```
One-time payment:
  User clicks "Buy" → pays ₹399 → gets 1200 credits → done.
  Next time they want credits, they buy again manually.
```

What a subscription is:

```
Subscription:
  User clicks "Subscribe to Pro" → pays ₹399/month → gets 1200 credits NOW
  → 30 days later, Razorpay automatically charges ₹399 again → 1200 more credits
  → 30 days later, again... (until they cancel)
```

The key difference: **you don't charge the user again**. Razorpay does it automatically on a schedule. Your job is to **listen for "payment happened" events** and give the user their credits.

### Key vocabulary

| Term | Meaning |
|------|---------|
| **Plan** | A template: "Pro Monthly — ₹399/month, 1200 credits." Created once, reused for every subscriber. |
| **Subscription** | A specific user subscribing to a specific plan. Has a start date, billing cycle, and status. |
| **Invoice** | Auto-generated by Razorpay each billing cycle. Represents one charge attempt. |
| **Billing Cycle** | The recurring period (monthly, weekly, yearly, etc.) |
| **Mandate** | Permission the user gives to auto-debit their account. For UPI: a "UPI mandate." For cards: a saved token. |
| **Trial Period** | Optional free period before the first charge. E.g., "7-day free trial, then ₹399/month." |

### "Do I run a script every month?"

**No.** This is the most common beginner question. Here's how it actually works:

```
                You (one time)         Razorpay (automatic)         You (on each event)
                ─────────────          ────────────────────         ────────────────────
Step 1:   Create a Plan                                                   
Step 2:   User subscribes →      Razorpay stores the mandate
Step 3:                          Day 1: charges user             → Webhook: "charged" → add credits
Step 4:                          Day 31: charges user again      → Webhook: "charged" → add credits
Step 5:                          Day 61: charges user again      → Webhook: "charged" → add credits
          ...                    ...                              ...
```

You write code for steps 1, 2, and the webhook handler. Razorpay handles the actual recurring billing.

## Part B — Razorpay Subscriptions API

### Creating a Plan (one-time setup)

A Plan is like a product listing. You create it once:

```python
import razorpay

client = razorpay.Client(auth=("rzp_test_xxx", "secret_xxx"))

plan = client.plan.create({
    "period": "monthly",        # monthly, weekly, yearly, daily
    "interval": 1,              # every 1 month
    "item": {
        "name": "Pro Monthly",
        "amount": 39900,        # ₹399 in paise
        "currency": "INR",
        "description": "1200 credits per month"
    }
})

print(plan["id"])  # "plan_ABC123" — save this
```

**You can also create plans from the Razorpay Dashboard** (no code needed):
Dashboard → Subscriptions → Plans → Create Plan

The `plan_id` is what you store in your config or database. You don't recreate it — one plan can have thousands of subscribers.

### Creating a Subscription (when a user subscribes)

```python
subscription = client.subscription.create({
    "plan_id": "plan_ABC123",
    "total_count": 12,          # max 12 billing cycles (or 0 for unlimited)
    "quantity": 1,
    "customer_notify": 1,       # Razorpay sends email/SMS to user
    # "start_at": 1735689600,   # optional: delay start (Unix timestamp)
    # "offer_id": "offer_xxx",  # optional: apply a discount/trial offer
})

print(subscription["id"])          # "sub_XYZ789"
print(subscription["short_url"])   # payment link for the user
print(subscription["status"])      # "created"
```

The `short_url` is what you show the user or redirect them to. They complete payment there (card, UPI, etc.).

### Subscription lifecycle (states)

```
created ──→ authenticated ──→ active ──→ completed
                │                │
                │                ├──→ halted (payment failures)
                │                │       │
                │                │       └──→ cancelled
                │                │
                │                └──→ cancelled (user/you cancelled)
                │
                └──→ expired (user never authenticated)
```

| State | Meaning |
|-------|---------|
| `created` | Subscription created, waiting for user to authorize payment |
| `authenticated` | User authorized (mandate approved) but first charge hasn't happened yet |
| `active` | At least one successful charge; subscription is running |
| `halted` | Razorpay tried to charge but failed repeatedly; auto-retry stopped |
| `cancelled` | Subscription was cancelled (by API call or dashboard) |
| `completed` | All planned billing cycles finished |
| `expired` | User never authenticated within the time window |

### Fetching subscription status

```python
sub = client.subscription.fetch("sub_XYZ789")
print(sub["status"])             # "active"
print(sub["current_start"])      # Unix timestamp of current cycle start
print(sub["current_end"])        # Unix timestamp of current cycle end
print(sub["paid_count"])         # number of successful charges so far
print(sub["remaining_count"])    # cycles remaining
```

### Cancelling a subscription

```python
# Option 1: Cancel at end of current billing cycle (user keeps access until then)
client.subscription.cancel("sub_XYZ789", {"cancel_at_cycle_end": 1})

# Option 2: Cancel immediately (access stops now)
client.subscription.cancel("sub_XYZ789", {"cancel_at_cycle_end": 0})
```

## Part C — Webhooks deep-dive

### What are webhooks?

You already use webhooks in this project for one-time payments. Quick recap:

```
Normal API call:     YOUR CODE calls Razorpay  →  "Create order"  →  response
Webhook:             RAZORPAY calls YOUR CODE  →  "Payment happened"  →  you react
```

A webhook is **Razorpay sending YOU an HTTP request** when something happens. You don't poll or check — you just have an endpoint waiting.

### How your existing webhook works

```python
# app/routers/payment.py — already in the codebase
@router.post("/webhook")
async def razorpay_webhook(request: Request):
    raw_body = await request.body()
    signature = request.headers.get("X-Razorpay-Signature", "")

    # Verify it's really from Razorpay (HMAC check)
    if not pay_svc.verify_webhook_signature(raw_body, signature):
        raise HTTPException(status_code=400, detail="Invalid webhook signature")

    event = json.loads(raw_body)
    event_type = event.get("event", "")
    # ... handle based on event_type
```

### Subscription webhook events

When you add subscriptions, Razorpay will send these new event types to the same webhook URL:

#### `subscription.authenticated`
**When:** User approved the mandate (UPI auto-debit permission or card saved).
**What to do:** Update subscription status to `authenticated` in your DB. No credits yet.

```json
{
    "event": "subscription.authenticated",
    "payload": {
        "subscription": {
            "entity": {
                "id": "sub_XYZ789",
                "plan_id": "plan_ABC123",
                "status": "authenticated",
                "customer_id": "cust_xxx"
            }
        }
    }
}
```

#### `subscription.activated`
**When:** First payment succeeded. Subscription is now live.
**What to do:** Update status to `active`. Add credits for the first cycle.

#### `subscription.charged`
**When:** A recurring payment succeeded (each cycle).
**What to do:** Add credits for this cycle. Record the invoice/payment.

This is the **most important** event for your credit system:
```json
{
    "event": "subscription.charged",
    "payload": {
        "subscription": {
            "entity": {
                "id": "sub_XYZ789",
                "plan_id": "plan_ABC123",
                "status": "active",
                "paid_count": 3,
                "current_start": 1712700000,
                "current_end": 1715292000
            }
        },
        "payment": {
            "entity": {
                "id": "pay_ABC123",
                "amount": 39900,
                "status": "captured",
                "invoice_id": "inv_xxx"
            }
        }
    }
}
```

#### `subscription.pending`
**When:** A charge attempt is in progress (common with UPI — mandate processing takes time).
**What to do:** Update status to `pending`. Wait for `charged` or `halted`.

#### `subscription.halted`
**When:** Razorpay tried to charge but failed after all retries (usually 3 attempts over ~7 days).
**What to do:** Mark subscription as `halted`. **Stop giving credits.** Notify user to fix their payment method.

#### `subscription.cancelled`
**When:** Subscription was cancelled (by you or the user via Razorpay dashboard).
**What to do:** Update status. If `cancel_at_cycle_end` was used, the user keeps access until `current_end`.

#### `subscription.completed`
**When:** All planned billing cycles finished (e.g., 12/12 months done).
**What to do:** Mark as completed. No more auto-charges will happen.

#### `subscription.paused` / `subscription.resumed`
**When:** You paused/resumed the subscription via API.
**What to do:** Update status accordingly.

### Webhook event flow for a typical subscription

```
Day 0:  User subscribes
           → subscription.authenticated  (mandate approved)
           → subscription.activated      (first charge succeeded)
           → subscription.charged        (first cycle payment)

Day 30: Razorpay auto-charges
           → subscription.charged        (second cycle)

Day 60: Razorpay tries to charge, UPI balance low
           → subscription.pending        (attempt in progress)
        Razorpay retries after 3 days — succeeds
           → subscription.charged        (third cycle)

Day 90: Razorpay tries to charge, mandate revoked
           → subscription.pending
        Retry 1 fails, Retry 2 fails, Retry 3 fails
           → subscription.halted         (auto-retry exhausted)

User fixes payment method and re-subscribes...
```

### Setting up the webhook in Razorpay Dashboard

1. Go to Razorpay Dashboard → Settings → Webhooks
2. Add webhook URL: `https://your-domain.com/payments/webhook`
3. Select events: check all `subscription.*` events (plus the existing `payment.*` ones)
4. Set the webhook secret (same `RAZORPAY_WEBHOOK_SECRET` you already use)

## Part D — UPI mandate failures and edge cases

### What is a UPI mandate?

When a user pays with UPI for a subscription, they don't just pay once — they also **authorize future auto-debits** through their UPI app (GPay, PhonePe, etc.). This authorization is called a "mandate."

```
User flow:
1. Your app shows "Subscribe for ₹399/month"
2. User clicks → redirected to Razorpay checkout
3. User selects UPI → opens their UPI app
4. UPI app shows: "Authorize auto-debit of up to ₹399/month to <Company>"
5. User approves → mandate is created
6. First payment is charged immediately
7. Every month, Razorpay auto-debits via this mandate
```

### When mandate creation fails

| Scenario | What happens | What you get |
|----------|-------------|-------------|
| User declines the mandate | Subscription stays in `created` | No webhook (or `subscription.expired` after timeout) |
| UPI app times out | Same as above | No event |
| Bank rejects the mandate | Subscription stays in `created` | No event |
| User's UPI app doesn't support mandates | Checkout shows error | No event |

**What to do:** Show the user "Subscription setup failed, please try again." Don't give credits.

### When a recurring charge fails

| Scenario | What happens | What you get |
|----------|-------------|-------------|
| Insufficient UPI balance | Razorpay retries (3 times over ~7 days) | `subscription.pending` → eventually `subscription.charged` or `subscription.halted` |
| User revoked mandate from UPI app | Can't charge anymore | `subscription.halted` |
| Bank downtime | Razorpay retries | `subscription.pending` → usually `subscription.charged` after retry |
| Mandate expired (some banks set expiry) | Can't charge | `subscription.halted` |

### Razorpay's automatic retry logic

You do NOT build retry logic yourself. Razorpay handles it:

```
Charge attempt 1: Day 0 (billing date)
  → Failed
Charge attempt 2: Day 3
  → Failed
Charge attempt 3: Day 7
  → Failed
  → subscription.halted (Razorpay gives up)
```

You can configure retry settings in the Razorpay Dashboard.

### What to do when subscription is halted

1. Mark subscription as `halted` in your DB
2. **Stop adding credits** (they haven't paid)
3. Optionally: give a **grace period** (e.g., 3 days of access after halt)
4. Notify the user: "Your subscription payment failed. Please update your payment method."
5. Show a "Reactivate" button that creates a new subscription

### Card subscriptions vs UPI — difference

| Aspect | Card (Visa/Mastercard) | UPI (GPay/PhonePe) |
|--------|----------------------|---------------------|
| Authorization | Card token saved at Razorpay | UPI mandate approved in user's app |
| Charge mechanism | Razorpay charges the card directly | Razorpay sends auto-debit request via UPI |
| Failure rate | Lower (card usually has credit limit) | Higher (depends on bank balance) |
| User control | Can't easily "revoke" from card app | Can revoke mandate anytime from UPI app |
| Supported amount | Usually no limit | Some banks cap mandate amounts |

## Part E — Trial, Cancel, Refund linkage

### Trial periods

A trial gives users free access before the first charge:

```python
# Create subscription with 7-day trial
subscription = client.subscription.create({
    "plan_id": "plan_ABC123",
    "total_count": 12,
    "start_at": int((datetime.now() + timedelta(days=7)).timestamp()),
    # First charge happens 7 days from now
})
```

Or use Razorpay Offers for more complex trials (percentage off first month, etc.).

**Timeline with trial:**
```
Day 0:  User subscribes → mandate approved → subscription.authenticated
        (User gets access but is NOT charged)
Day 7:  Trial ends → Razorpay charges → subscription.activated + subscription.charged
        (First real payment, add credits)
Day 37: Second charge → subscription.charged
        ...
```

**What if user cancels during trial?**
- They were never charged → no refund needed
- Mark subscription as cancelled, remove access

### Cancellation

Two options:

**Option 1: Cancel at cycle end** (recommended for good UX)
```python
client.subscription.cancel(sub_id, {"cancel_at_cycle_end": 1})
```
- User keeps access until current billing cycle ends
- No refund needed (they already paid for this period)
- After cycle ends, subscription moves to `cancelled`

**Option 2: Cancel immediately**
```python
client.subscription.cancel(sub_id, {"cancel_at_cycle_end": 0})
```
- Access stops immediately
- You might want to refund the remaining days of the current cycle (pro-rata)

### Refund linkage

To refund a subscription payment, you need the `razorpay_payment_id` from the invoice:

```python
# 1. Get the latest payment ID from your subscription_invoices table
# 2. Use the existing refund_payment function:
from app.services.payment import refund_payment

refund = refund_payment(
    razorpay_payment_id="pay_ABC123",   # from the invoice
    amount_paise=39900,                  # full refund, or calculate pro-rata
)
```

For **pro-rata refund** (refunding unused days):
```python
import math
from datetime import datetime

def calculate_prorata_refund(current_start, current_end, cancel_date, full_amount):
    total_days = (current_end - current_start).days
    used_days = (cancel_date - current_start).days
    remaining_days = total_days - used_days
    refund_amount = math.floor(full_amount * remaining_days / total_days)
    return refund_amount
```

## Part F — Database design for subscriptions

### New tables needed

#### Table: `subscription_plans`

```sql
CREATE TABLE IF NOT EXISTS subscription_plans (
    id              VARCHAR(36)  PRIMARY KEY,
    razorpay_plan_id VARCHAR(64) UNIQUE NOT NULL,
    name            VARCHAR(128) NOT NULL,
    credits_per_cycle INTEGER    NOT NULL,
    price_paise     INTEGER      NOT NULL,
    currency        VARCHAR(3)   NOT NULL DEFAULT 'INR',
    period          VARCHAR(16)  NOT NULL DEFAULT 'monthly',
    interval_count  INTEGER      NOT NULL DEFAULT 1,
    trial_days      INTEGER      NOT NULL DEFAULT 0,
    is_active       BOOLEAN      NOT NULL DEFAULT true,
    features        JSONB,                              -- for future plan-based gating
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ  NOT NULL DEFAULT now()
);
```

#### Table: `user_subscriptions`

```sql
CREATE TABLE IF NOT EXISTS user_subscriptions (
    id                      VARCHAR(36)  PRIMARY KEY,
    user_id                 VARCHAR(128) NOT NULL,
    plan_id                 VARCHAR(36)  NOT NULL REFERENCES subscription_plans(id),
    razorpay_subscription_id VARCHAR(64) UNIQUE NOT NULL,
    status                  VARCHAR(24)  NOT NULL DEFAULT 'created',
    current_start           TIMESTAMPTZ,
    current_end             TIMESTAMPTZ,
    trial_end               TIMESTAMPTZ,
    paid_count              INTEGER      NOT NULL DEFAULT 0,
    cancel_at_cycle_end     BOOLEAN      NOT NULL DEFAULT false,
    mandate_type            VARCHAR(16),       -- 'upi', 'card', 'emandate'
    created_at              TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at              TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_user_subs_user
    ON user_subscriptions (user_id, status);

CREATE INDEX IF NOT EXISTS idx_user_subs_rz
    ON user_subscriptions (razorpay_subscription_id);
```

#### Table: `subscription_invoices`

```sql
CREATE TABLE IF NOT EXISTS subscription_invoices (
    id                      VARCHAR(36)  PRIMARY KEY,
    subscription_id         VARCHAR(36)  NOT NULL REFERENCES user_subscriptions(id),
    razorpay_invoice_id     VARCHAR(64),
    razorpay_payment_id     VARCHAR(64),
    amount                  INTEGER      NOT NULL,
    status                  VARCHAR(16)  NOT NULL DEFAULT 'pending',
    cycle_number            INTEGER      NOT NULL,
    created_at              TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at              TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_sub_invoices_sub
    ON subscription_invoices (subscription_id);
```

### How these tables connect to existing ones

```
subscription_plans          (your plan templates)
       │
       ▼
user_subscriptions          (user X subscribes to plan Y)
       │
       ├──→ subscription_invoices    (each monthly charge)
       │          │
       │          └──→ razorpay_payment_id → can be used for refunds
       │
       └──→ on each "charged" webhook:
              add_credits(user_id, credits_per_cycle)
                 │
                 ├──→ api_user_credits       (balance updated)
                 └──→ razorpay_credit_transactions  (ledger entry)
```

Credits still flow through your **existing** `add_credits()` function. Subscriptions are just a new way to trigger credit additions.

### Step 4: Service functions

Create `app/services/subscription.py`:

**Note:** The production code in this repo uses **`list_plans()`** (ordered catalog, JSONB `features`) and **`create_plan_and_persist()`** for admin plan creation, not a bare `SELECT *` helper. See [09 — Subscription dev guide](./09-subscription-dev-guide.md) (Parts C.3, E–G). The **`get_plans()`** snippet below is a minimal teaching example.

```python
import uuid
from datetime import datetime, timezone
from typing import Optional

import razorpay
from loguru import logger

from app.utils.config_utils import get_config
from app.utils.db_utils import execute_query_with_params
from app.services.payment import add_credits, refund_payment

_rz_key_id = get_config("RAZORPAY_KEY_ID")
_rz_key_secret = get_config("RAZORPAY_KEY_SECRET")
rz_client = razorpay.Client(auth=(_rz_key_id, _rz_key_secret))


def get_plans() -> list[dict]:
    sql = "SELECT * FROM subscription_plans WHERE is_active = true"
    return execute_query_with_params(sql, {}, to_dict=True)


def get_plan(plan_id: str) -> Optional[dict]:
    sql = "SELECT * FROM subscription_plans WHERE id = :plan_id AND is_active = true"
    rows = execute_query_with_params(sql, {"plan_id": plan_id}, to_dict=True)
    return rows[0] if rows else None


def create_subscription(user_id: str, plan_id: str) -> dict:
    plan = get_plan(plan_id)
    if not plan:
        raise ValueError("Plan not found or inactive")

    # Create subscription on Razorpay
    rz_sub = rz_client.subscription.create({
        "plan_id": plan["razorpay_plan_id"],
        "total_count": 120,     # max cycles
        "quantity": 1,
        "customer_notify": 1,
    })

    # Save to DB
    sub_id = str(uuid.uuid4())
    sql = """
        INSERT INTO user_subscriptions
            (id, user_id, plan_id, razorpay_subscription_id, status, created_at, updated_at)
        VALUES (:id, :user_id, :plan_id, :rz_sub_id, :status, :now, :now)
    """
    execute_query_with_params(sql, {
        "id": sub_id,
        "user_id": user_id,
        "plan_id": plan_id,
        "rz_sub_id": rz_sub["id"],
        "status": "created",
        "now": datetime.now(timezone.utc).isoformat(),
    })

    return {
        "subscription_id": sub_id,
        "razorpay_subscription_id": rz_sub["id"],
        "short_url": rz_sub.get("short_url", ""),
        "status": "created",
    }


def handle_subscription_charged(rz_sub_id: str, payment_entity: dict) -> None:
    """Called from webhook when subscription.charged fires."""
    sub = _get_sub_by_rz_id(rz_sub_id)
    if not sub:
        logger.warning("Webhook: subscription {} not found in DB", rz_sub_id)
        return

    plan = get_plan(sub["plan_id"])
    if not plan:
        logger.error("Webhook: plan {} not found for sub {}", sub["plan_id"], rz_sub_id)
        return

    rz_payment_id = payment_entity.get("id", "")

    # Idempotency: check if we already recorded this invoice
    existing = _get_invoice_by_payment(rz_payment_id)
    if existing:
        logger.info("Webhook: payment {} already processed for sub {}", rz_payment_id, rz_sub_id)
        return

    # Record the invoice
    _save_invoice(sub["id"], payment_entity)

    # Add credits
    add_credits(
        user_id=str(sub["user_id"]),
        amount=plan["credits_per_cycle"],
        reason="subscription",
        reference_id=rz_payment_id,
    )

    # Update subscription status and paid_count
    _update_sub_status(rz_sub_id, "active", paid_count_increment=1)

    logger.info("Webhook: credited {} credits for subscription {} cycle",
                plan["credits_per_cycle"], rz_sub_id)


def handle_subscription_halted(rz_sub_id: str) -> None:
    _update_sub_status(rz_sub_id, "halted")
    logger.warning("Subscription {} halted — payment retries exhausted", rz_sub_id)


def handle_subscription_cancelled(rz_sub_id: str) -> None:
    _update_sub_status(rz_sub_id, "cancelled")
    logger.info("Subscription {} cancelled", rz_sub_id)


def cancel_subscription(user_id: str, rz_sub_id: str, at_cycle_end: bool = True) -> dict:
    sub = _get_sub_by_rz_id(rz_sub_id)
    if not sub:
        raise ValueError("Subscription not found")
    if str(sub["user_id"]) != user_id:
        raise ValueError("Subscription does not belong to this user")

    rz_client.subscription.cancel(rz_sub_id, {"cancel_at_cycle_end": 1 if at_cycle_end else 0})

    new_status = "cancelled" if not at_cycle_end else sub["status"]
    _update_sub_status(rz_sub_id, new_status, cancel_at_cycle_end=at_cycle_end)

    return {"subscription_id": sub["id"], "status": new_status, "cancel_at_cycle_end": at_cycle_end}


# ── Internal helpers ──────────────────────────────────────────────

def _get_sub_by_rz_id(rz_sub_id: str) -> Optional[dict]:
    sql = "SELECT * FROM user_subscriptions WHERE razorpay_subscription_id = :rz_sub_id"
    rows = execute_query_with_params(sql, {"rz_sub_id": rz_sub_id}, to_dict=True)
    return rows[0] if rows else None


def _get_invoice_by_payment(rz_payment_id: str) -> Optional[dict]:
    sql = "SELECT * FROM subscription_invoices WHERE razorpay_payment_id = :pid"
    rows = execute_query_with_params(sql, {"pid": rz_payment_id}, to_dict=True)
    return rows[0] if rows else None


def _save_invoice(subscription_id: str, payment_entity: dict) -> None:
    sql = """
        INSERT INTO subscription_invoices
            (id, subscription_id, razorpay_invoice_id, razorpay_payment_id, amount, status, cycle_number, created_at, updated_at)
        VALUES (:id, :sub_id, :inv_id, :pay_id, :amount, :status, :cycle, :now, :now)
    """
    execute_query_with_params(sql, {
        "id": str(uuid.uuid4()),
        "sub_id": subscription_id,
        "inv_id": payment_entity.get("invoice_id"),
        "pay_id": payment_entity.get("id"),
        "amount": payment_entity.get("amount", 0),
        "status": "paid",
        "cycle": 0,     # you can track cycle number from subscription.paid_count
        "now": datetime.now(timezone.utc).isoformat(),
    })


def _update_sub_status(rz_sub_id: str, status: str,
                       paid_count_increment: int = 0,
                       cancel_at_cycle_end: Optional[bool] = None) -> None:
    parts = ["status = :status", "updated_at = :now"]
    params = {"rz_sub_id": rz_sub_id, "status": status, "now": datetime.now(timezone.utc).isoformat()}

    if paid_count_increment:
        parts.append("paid_count = paid_count + :inc")
        params["inc"] = paid_count_increment

    if cancel_at_cycle_end is not None:
        parts.append("cancel_at_cycle_end = :cace")
        params["cace"] = cancel_at_cycle_end

    sql = f"UPDATE user_subscriptions SET {', '.join(parts)} WHERE razorpay_subscription_id = :rz_sub_id"
    execute_query_with_params(sql, params)
```

### I.3 — How much money have I received?

**One-time payments (credit pack purchases):**

```sql
-- Total revenue from one-time purchases
SELECT
    SUM(amount) / 100.0 AS total_revenue_inr,
    COUNT(*)             AS payment_count
FROM razorpay_orders
WHERE status = 'paid';

-- Revenue by month
SELECT
    DATE_TRUNC('month', created_at) AS month,
    SUM(amount) / 100.0             AS revenue_inr,
    COUNT(*)                         AS payments
FROM razorpay_orders
WHERE status = 'paid'
GROUP BY DATE_TRUNC('month', created_at)
ORDER BY month DESC;

-- Revenue by package
SELECT
    package_id,
    SUM(amount) / 100.0 AS revenue_inr,
    COUNT(*)             AS purchases
FROM razorpay_orders
WHERE status = 'paid'
GROUP BY package_id;
```

**Subscription revenue (after you build the subscription module):**

```sql
-- Total subscription revenue
SELECT
    SUM(amount) / 100.0 AS total_revenue_inr,
    COUNT(*)             AS invoice_count
FROM subscription_invoices
WHERE status = 'paid';

-- Subscription revenue by month
SELECT
    DATE_TRUNC('month', created_at) AS month,
    SUM(amount) / 100.0             AS revenue_inr,
    COUNT(*)                         AS invoices
FROM subscription_invoices
WHERE status = 'paid'
GROUP BY DATE_TRUNC('month', created_at)
ORDER BY month DESC;
```

**Combined revenue (both sources):**

```sql
SELECT source, SUM(amount_inr) AS total_inr, SUM(count) AS total_payments
FROM (
    SELECT 'one_time' AS source, SUM(amount)/100.0 AS amount_inr, COUNT(*) AS count
    FROM razorpay_orders WHERE status = 'paid'
    UNION ALL
    SELECT 'subscription', SUM(amount)/100.0, COUNT(*)
    FROM subscription_invoices WHERE status = 'paid'

GROUP BY source;
```

### I.4 — Settlement reconciliation (money in your bank)

Razorpay does **not** transfer money to your bank instantly. There is a settlement cycle:

```
Payment captured               Settlement arrives
     │                              │
     ▼                              ▼
  Day 0  ──── T+2 business days ──── Day 2-3
  (user pays)                    (money in your bank)

  For new accounts: T+7 business days
```

**What Razorpay deducts before settlement:**

```
Settlement amount = Captured amount
                  − Razorpay fee (typically 2%)
                  − GST on Razorpay fee (18% of fee)
                  − Refunds issued
                  − Adjustments
```

**Example:**

```
Captured:    ₹399.00
Razorpay fee: ₹7.98  (2%)
GST on fee:   ₹1.44  (18% of ₹7.98)
─────────────────────
Net settled:  ₹389.58
```

**View settlements via Dashboard:**

Go to Transactions → Settlements. Each row is a settlement batch. Click to see every payment included.

**View via API:**

```python
# Fetch all settlements
settlements = client.settlement.all({"count": 50})
for s in settlements["items"]:
    print(f"ID: {s['id']}, Amount: ₹{s['amount']/100:.2f}, "
          f"Status: {s['status']}, Created: {s['created_at']}")

# Detailed settlement report for a month
report = client.settlement.report({
    "year": 2026,
    "month": 1,
})
# Returns every transaction in that month's settlements:
# payments, refunds, adjustments, fees, taxes
```

**Match your DB to settlements:**

```sql
-- Your DB: daily captured revenue
SELECT
    DATE(created_at) AS day,
    SUM(amount) / 100.0 AS captured_inr,
    COUNT(*) AS payments
FROM razorpay_orders
WHERE status = 'paid'
GROUP BY DATE(created_at)
ORDER BY day DESC
LIMIT 30;
```

Compare this with the Razorpay settlement report. The `captured_inr` from your DB should match the sum of payment amounts in the settlement report for the same date. The **settled** amount will be lower (after fees and GST).

**Step 7: Cross-check credit ledger**

This is critical — ensures credits given match payments received.

```sql
-- Credits issued from purchases
SELECT SUM(amount) AS credits_from_purchases
FROM razorpay_credit_transactions
WHERE transaction_type = 'credit' AND reason = 'purchase'
  AND created_at >= '2026-01-01' AND created_at < '2026-02-01';

-- Credits issued from subscriptions
SELECT SUM(amount) AS credits_from_subscriptions
FROM razorpay_credit_transactions
WHERE transaction_type = 'credit' AND reason = 'subscription'
  AND created_at >= '2026-01-01' AND created_at < '2026-02-01';

SELECT SUM(amount) AS credits_refunded
FROM razorpay_credit_transactions
WHERE transaction_type = 'refund'
```

### I.6 — Alerting and monitoring (what to watch in production)

These are the things that will go wrong in a live system. Monitor them.

**1. Webhook failure rate**

Go to Razorpay Dashboard → Settings → Webhooks. Each webhook shows delivery attempts and status. If you see persistent failures, your webhook endpoint is down or rejecting requests.

**2. Orders stuck in `created` status**

```sql
-- Orders created more than 30 minutes ago that never moved to paid/failed
SELECT id, user_id, razorpay_order_id, amount / 100.0 AS amount_inr, created_at
FROM razorpay_orders
WHERE status = 'created'
  AND created_at < NOW() - INTERVAL '30 minutes'
ORDER BY created_at DESC;
```

These are users who started checkout but never completed. A few are normal (user abandoned). Many in a row means your checkout or webhook is broken.

**3. Subscriptions in `halted` status**

```sql
-- Users who are paying customers but their payment failed
SELECT us.user_id, sp.name, us.razorpay_subscription_id, us.updated_at
FROM user_subscriptions us
JOIN subscription_plans sp ON us.plan_id = sp.id
WHERE us.status = 'halted'
ORDER BY us.updated_at DESC;
```

These users need to update their payment method. You should notify them.

**4. Credit balance mismatch**

```sql
-- Find users where balance doesn't match ledger
SELECT
    uc.user_id,
    uc.balance AS stored_balance,
    COALESCE(SUM(CASE WHEN ct.transaction_type = 'credit' THEN ct.amount ELSE 0 END), 0)
    - COALESCE(SUM(CASE WHEN ct.transaction_type IN ('debit', 'refund') THEN ct.amount ELSE 0 END), 0)
    AS calculated_balance
FROM api_user_credits uc
LEFT JOIN razorpay_credit_transactions ct ON uc.user_id = ct.user_id
GROUP BY uc.user_id, uc.balance
HAVING uc.balance != (
    COALESCE(SUM(CASE WHEN ct.transaction_type = 'credit' THEN ct.amount ELSE 0 END), 0)
    - COALESCE(SUM(CASE WHEN ct.transaction_type IN ('debit', 'refund') THEN ct.amount ELSE 0 END), 0)
);
```

If this returns rows, something wrote to `api_user_credits` without going through the ledger, or a ledger entry failed. Investigate immediately.

**5. Revenue anomaly check**

```sql
-- Daily revenue for the past 7 days — look for sudden drops
SELECT
    DATE(created_at) AS day,
    SUM(amount) / 100.0 AS revenue_inr,
    COUNT(*) AS payments
FROM razorpay_orders
WHERE status = 'paid'
  AND created_at >= NOW() - INTERVAL '7 days'
GROUP BY DATE(created_at)
ORDER BY day DESC;
```

A sudden drop to zero means checkout or webhooks are broken. A gradual decline might be normal traffic patterns.
